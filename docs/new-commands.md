# Chapter 23A Discord commands

This chapter implements the server-only command-verification slice of specification §23. It does not enable DM-only mode, model/reasoning selection, settings reset, or the other C-priority operations. Read-only model catalog, guarded Session-title rename, a limited readonly Native context projection and a narrow explicitly confirmed Native Compact command path are registered. Title rename has no Native CAS and is not an AC-44/45 concurrency guarantee; projection and Compact source/fixture coverage are not live Native/Discord acceptance. Discord command registration remains an explicit authenticated GUI action; this work does not register commands against Discord. Folder configuration is optional for saving/connecting. An empty allowlist grants no Session access until an operator adds a folder in the GUI or with `/agent workspace-add`. The command updates the saved revision and disarms future auto-start, without stopping the current receiver; stale GUI saves are rejected.

## Registered surface

The `/agent` root has 20 top-level children (17 subcommands and 3 subcommand groups). The `context` group has `show` and `compact`; the `notifications` group has 3 subcommands. Each subcommand has at most 3 options, below Discord's 25-option limit at every hierarchy level.

| Command | Behavior and limits |
| --- | --- |
| `/agent help [topic]` | Lists implemented features and explains unsupported contract-dependent operations. |
| `/agent current` | Shows the selected, authorized Session; safe title, configured Workspace alias when it matches, observed busy state, Binding version, last-request model versus next model setting when Native metadata is present, and notification preferences. This is not a claim about the model of a currently active request. |
| `/agent context show` | For the exact authorized selected Session, performs a live-only Native Session lookup and requests only `contextPressure` / `contextBreakdown` via `sessionProjections.snapshot(session, keys)`. Whitelists up to six optional nonnegative safe-integer fields (`pressureTokens`, `projectedTokens`, `contextWindow`, `systemTokens`, `toolsTokens`, `messageTokens`) plus safe-integer fold cursor `asOfSeq`. Missing/malformed values stay unavailable. The aggregates are non-atomic; `asOfSeq` is not sample time, zero is not evidence of a fresh sample, and no occupancy/percentage/cost/currentness is inferred. Missing optional projection services do not disable core Host or Compact. |
| `/agent models [provider] [query] [page]` | Read-only view of the injected Native `modelCatalog()` when available. Displays routable provider/model/reasoning candidates with bounded output; failure details are omitted. This does not select a model. |
| `/agent compact confirm:true` / `/agent context compact confirm:true` | Explicitly runs the canonical Native Compact command for the selected, authorized ordinary Agent after idle/queue and target revalidation. It may change Session history; unknown outcomes are durable and never automatically replayed. An unresolved outcome fences only that exact full Session from further prompts, binding to it, and title mutation; this Bridge path has no clear/replay action. `/agent context show` is a separate limited projection, not current usage. Real Native/Discord acceptance remains unverified. |
| `/agent settings title value:<title> confirm-no-cas:true` | Renames only the currently selected, authorized idle Session through the injected Native `rename()` method, rechecks Binding and reads back the normalized title. The explicit flag acknowledges that the Native endpoint has no title CAS; external Desktop races cannot be prevented. `/agent rename` is a compatibility alias. |
| `/agent workspaces` | Lists configured aliases only; never returns local paths. |
| `/agent workspace-add alias:<new> path:<absolute> confirm-access:true` | Allows an existing directory after connection. Requires configured user/Guild/Channel and explicit access confirmation. Adds at most 32 aliases, never overwrites an alias or selects/creates a Session. Persists before granting runtime access; revision conflicts fail closed. Changes neither credentials nor existing Runs. Paths are submitted to Discord as arguments, never echoed by the response; do not include secrets. |
| `/agent sessions [query] [page]` | Searches authorized non-subagent Sessions by case-insensitive substring of ID or title; page size is 5. |
| `/agent new workspace:<alias>` | Uses the configured alias and current Native `create` contract. Title/model/effort are not accepted; non-null injected/stale values are rejected before Native `create`. The created Session is then checked against the strict modern-page probe; if that post-create probe fails, the Native-created Session can remain unbound. |
| `/agent bind session:<id>` / `/agent unbind` | Selects an authorized Session / removes only the selection. |
| `/agent prompt text:<instruction>` | Sends the prompt through the existing Engine operation. |
| `/agent status [run]` | Reports the owned Run state and notification state; approval status is not available through the current Native contract. |
| `/agent tasks [state] [page]` | Lists only Runs owned by the invoking user and exact Guild/Channel, in currently allowed Sessions; page size is 5. |
| `/agent result [run] [page]` | Calls the Engine's correlated result-page service; it never substitutes another Run's output. |
| `/agent notify run:<id>` | Compatibility alias for notification retry; does not resubmit a prompt. Unknown legacy delivery is refused. |
| `/agent notifications show` | Shows the destination and authorized User/Guild/Channel/Binding scope, plus pending, unknown/sending, blocked, incomplete, and undelivered-part counts. Progress notifications are explicitly unsupported. |
| `/agent notifications set destination:<dm\|origin> [confirm-origin]` | Changes the future-run preference for the invoking actor+Guild+Channel only. `origin` requires an existing selected Binding and explicit confirmation; the response echoes the authorized User/Guild/Channel/Binding/version scope. Existing Runs keep their pinned destination. There is no `progress` option because progress notifications are unsupported. |
| `/agent notifications retry delivery:<id> [part] [confirm-duplicate-risk]` | Retries delivery only. The Engine enforces next-unsent-part order and requires explicit duplicate-risk confirmation for an unknown part. It does not call Native prompt. |
| `/agent diagnose` | Performs an authorized Session-list connectivity check and reports only public adapter-method availability plus safe error codes; it does not expose tokens, paths, raw errors, or secret settings. |

All operations are authorized against the configured user, Guild, and Channel even though this command is guild-only. Session list/current reads are limited to permitted Workspace Sessions. History is unregistered and fails closed. Run listing and result access are restricted to the exact initiating user/Guild/Channel. Session IDs and Run IDs are not shortened in responses.

The work-start notice is emitted only after a complete Native observation correlates the exact Run request `rpcId` with the appended user message inside its matching `turn/start` → `step/start` sequence; it does not treat prompt acceptance or queue admission as execution. It uses the pinned, authorized destination, persists an unknown-before-send fence, suppresses contaminated/terminal same-poll observations, and never auto-replays unknown sends. Explicit receiver stop or replacement (not an automatic Discord SDK gateway reconnect) aborts Bridge waits for lookup/send within a deadline; the race does not cancel the underlying SDK request. A send that already started stays unknown.

## Explicitly unavailable

The checked Host service exposes optional `sessionController.modelCatalog()` and `sessionController.rename()` methods, consumed only when present on the injected controller. Catalog fields are whitelisted and raw provider failure text is never exposed. Title rename targets the exact Session but has no expected-revision/CAS parameter; the command therefore requires explicit `confirm-no-cas:true`, authorized same-Session Binding revalidation, empty/valid Native queues, no tracked active/unknown Run, and readback. This narrows the local operation but cannot serialize a Desktop/external rename race. The model-selection Host operation also writes shared owner-profile defaults, so `/agent model` and reasoning-setting mutation remain disabled. Settings reset remains unavailable. Context display is limited to the selected live Session and the two selected aggregate views; it makes no cold Session resolution and emits no unselected projection fields. Projection services are optional and independent of required Host/Compact services. `contextPressure` and `contextBreakdown` are separate/non-atomic; `asOfSeq` is the snapshot fold tail, not a usage-sample timestamp/sequence. Values can be stale or missing and do not prove measured occupancy, currentness, percentage or cost. The broader `projections()` response and live `stateOf()` data are not substitutes.

**History unavailable:** the Native semantic `sessionQuery.filterEvents(sessionId,filters)` exists, but it does not provide a role/output selector, bounded cursor pagination/byte cap, or signal; assistant text may include flattened tool-call names/arguments even though reasoning blocks are removed. It therefore cannot satisfy the bridge's private-field exclusion and bounded-response requirements. The controller's `page(request,signal)` is a different contiguous event-page API, not a safe substitute. `/agent history` remains unregistered; a stale/injected invocation is rejected before snapshot/page/events/history calls. This does not disable the existing Engine event correlation or `/agent result` recovery/output paging.

The remaining C-priority bridge operations are unregistered and disabled: targeted `stop`, external `approval`, shared FIFO `queue`, `files`/Artifact transfer, and `chat enable/disable`. Native Compact has the narrow command path listed above; its synthetic Engine/Host and adapter-contract tests do not establish live Native behavior or full-spec acceptance. File input still requires secure Discord CDN ingestion, content/size validation, protected staged blobs and exact opaque Native upload receipts, with no upload/prompt replay. Image reachability is not arbitrary Artifact download. Queue updates are per pending Native MessageId, not the bridge's durable shared FIFO; Session cancel is not targeted to an exact Run; ApprovalService is not a verified external actor/scope/revision gate. Telegram code and command behavior remain unchanged.

The Bridge now locally protects terminal output bodies/parts in DPAPI payloads with a durable intent, quota, readback, exact Run/deployment scope and receipt-aware 7-day cleanup. This remains a partial OUT-08 implementation: no 90-day metadata pruning, complete power-loss/cross-process quota proof, official Native durable receipt, or live Host/Discord acceptance.

## DM-only mode: design/proof checklist only

No slash commands, message listener, authentication route, or live mutation enable DM operation. Completion DMs from existing notifications do not imply that DM interaction is supported.

- Define distinct tagged conversation identities, never a Guild-shaped key with null/zero IDs:
  - `DiscordGuildConversationKey = (transport=discord, kind=guild, botId, guildId, channelId, threadId | null)`
  - `DiscordDmConversationKey = (transport=discord, kind=dm, botId, userId, dmChannelId)`
- A future GUI must explicitly select `DM-only`, `server-only`, or `both`. Existing settings must not auto-migrate. DM-only setup still requires verified Bot/Application identity, the explicitly allowed User ID, Workspace authorization, and Native Session authorization; absence of Guild IDs never means allow-all.
- Verify official Discord User Install and global-command `integration_types`, `contexts` including `BOT_DM`, Gateway receive behavior, and authorized follow-up DMs. Guild registration or legacy `dm_permission` is not proof. No external HTTP endpoint or alternate receiver may be silently introduced.
- Validate Bot identity, real interaction context, `user.id`, and a true 1:1 DM channel/recipient on each operation. Reject non-owner Users, Bot/Webhook actors, group DMs, fake contexts, and forged/stale components with zero side effects. Never auto-promote the first DM sender.
- Preserve one active Binding per conversation and Native Session uniqueness: a Native Session cannot be bound to a Guild and DM simultaneously. Explicitly unbind before switching; never move existing Runs, their actor/session/destination, approvals, or outbox records.
- Keep ordinary DM messages inert. Initial operation, if proven, is slash-command-only. Any later explicit chat enable must apply only to new messages and cannot bypass approval, sandbox, or busy checks.
- Keep DM-only disabled until the actual install → command display → Gateway interaction → Native Session operation → long-running completion delivery flow has been verified on real Discord, including restart/reconnect and non-owner/group-DM denial. No live proof is claimed by this implementation.
