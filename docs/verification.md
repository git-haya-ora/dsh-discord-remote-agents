## Opt-in connection notices (0.2.0-restricted.8, local source only)

- Adds independent, default-off DM and channel checkboxes. Selecting both targets both explicitly; DMs go to configured allowed users, channel notices to configured allowed channels. Channel disclosure is warned about before saving. Existing settings without this field remain off. No receiver is started by selecting or saving these options.
- A successful receiver start schedules one bounded notice per enabled destination, not per poll or Gateway-ready replay. Session/project metadata comes only from the existing authorized channel Binding and the official Native Session summary. Last-used and next model metadata are distinct observations, not proof of current execution. Missing or inaccessible metadata is reported explicitly; the newest unrelated Session is never substituted. No prompt or history is fetched.
- Destination/actor/Guild checks are repeated after awaits; Binding version checks prevent ABA selection disclosure. Absolute-path output is suppressed, known secrets are redacted, and mentions/embeds are disabled. Session names are still potentially sensitive metadata: do not put secrets in them. DM failure does not redirect to a channel. Both independently opted-in destinations may be attempted.
- The Discord SDK's default retries are disabled. Channel/user routes reject rate-limit queuing rather than silently repeating a POST behind the uncertainty fence. Actual SDK 503/429 synthetic transport tests assert one network attempt; the existing final-answer path converts SDK rate-limit information into its explicit durable Engine deadline instead of bypassing ordering.
- Receipt metadata is fenced as unknown before the network send; no notice body is saved. Ambiguous or failed sends are never automatically retried, replayed after restart, or translated into a Native prompt. A new receiver instance is a new connection event. Delayed delivery does not block management status, and delivery failure leaves a successfully started receiver connected, with a separate safe notice warning.
- Independent review found that partial path replacement could disclose suffixes of paths containing spaces. The final sanitizer masks the entire metadata field when a path separator is present; only an explicitly recognized model identifier may retain its narrow provider/model namespace. Tests cover Windows/UNC/POSIX paths, spaces and non-whitespace boundaries, while preserving recognized model identifiers.
- Final frozen-source regression after the privacy fix: **242 passed, zero failures, zero skips**, including private Windows SQLite/DPAPI fixtures (98,476.7061 ms). Actual SDK 503/429 tests use synthetic transport, not live Discord. Earlier 230/239-test gates are superseded.
- Distribution parity passed for 40 files, archive inspection for 41 files / 24 JavaScript modules, and the known-pattern public-source scan for 160 files. `npm audit` reported zero vulnerabilities. These heuristic checks do not guarantee absence of every secret or PII. Final archive SHA256: `a821c58b2d986efc9f9c86132b02cef7fe9459ab63a590f04ed118b283317a0c`.
- This addition has not been installed or live-tested. No Discord token was read/tested, receiver started, commands registered, Native prompt submitted, or Git/npm publication performed for these checks. The installed restricted.7 Host-status evidence below is separate from this feature's offline tests.

## Optional workspace setup (0.2.0-restricted.6, historical stage)

- Saving/connecting accepts an empty workspace allowlist. Blank GUI rows do not make a folder mandatory; partially completed or invalid rows still fail locally. No folder access is granted by connecting alone.
- After connecting, `/agent workspace-add alias:<new> path:<existing-absolute-path> confirm-access:true` adds an allowlisted directory for the configured user/Guild/Channel. Existing aliases cannot be overwritten; the maximum remains 32. Filesystem identity is validated before persisting, and authorization is rechecked after the await. Persistence/revision failures do not grant runtime access; storage failures release the management lock.
- Registration increments the saved revision, rejects stale GUI saves and disarms future auto-start. It does not restart the receiver, read/change the token, change a Binding, create a Native Session or replay a prompt. Paths are submitted to Discord as command arguments but are not echoed in responses; never include secrets in them. Folder authorization is not an OS sandbox.
- Final full regression: 210 passed, zero failures and zero skips, with a private fixture parent. Generated distribution parity passed for 39 files; archive inspection passed for 40 files / 23 JavaScript modules. The public-source heuristic scan checked 157 files and passed; it is not universal secret/PII proof.
- The new flow is source/offline-test evidence only. This version has not been installed into the running DSH, and live commands were not registered. The separate upstream Host dependency failure below is still unresolved; optional folders must not be described as fixing that failure.

## Historical unsuccessful Host dependency attempt and Japanese settings (0.2.0-restricted.5)

- The installed Host failed with `cannot get property "webServer" without inject`. The Host entry now declares `webServer` alongside `connection` and `sessionController`; authenticated RPC registration is unchanged.
- The settings page adds a page-local Japanese/English/Chinese/DSH-language selector. Changing language makes no RPC call, does not persist settings or secrets, and preserves unsaved fields. Reopening the page returns to the DSH-language selection.
- The ordinary regression run reported 196 passed, zero failed and nine private-path fixture skips (205 total). Rerunning the protected-journal/DPAPI suites under a verified private fixture parent passed all 50 tests with zero skips, including the nine skipped cases.
- The first isolated check incorrectly provided Connection and `webServer` from the same context. Its successful route registration did **not** reproduce production service ownership and is not evidence of a working Host fix.
- A corrected check uses sibling providers and the installed official Cordis/Connection implementation. With the current Connection provider scope it fails with `cannot get property "webServer" without inject`, registers zero routes and invokes zero Native methods. Giving **only the synthetic Connection provider** an explicit `webServer` dependency permits route registration, still with zero Native calls. The plugin's own dependency declaration alone is insufficient.
- The installed Connection implementation declares `credentials`, and its RPC getter captures a service-shadowed owner whose route registration accesses `owner.webServer`. The affected web-host ownership/injection boundary requires an upstream-supported fix. The synthetic comparison is not a recommendation to make `webServer` mandatory in every Connection deployment; headless/carrier behavior needs upstream validation.
- The 40-file archive passed inspection (23 JavaScript modules), the 39-file generated distribution passed parity checks, and the public-source heuristic scan passed. These checks are not universal secret/PII proof.
- The archive was installed through the authenticated plugin manager, and Japanese controls were observed in the actual settings page. The official manager marks an update to an existing bundle as restart-required. After the user restarted DSH, the new process still reported one failed component and the **same** injection exception. Host connection recovery is therefore **not achieved**, rather than merely awaiting restart. Do not ask for another restart or a token to resolve this demonstrated dependency failure.
- No shared DSH process was killed, token read/tested, live command registered or Discord receiver started during this diagnosis. No ASAR edits, authentication bypasses or mutations of another service's dependency scope were used. Source changes have not been committed or published.

## Authenticated exact-route repair (0.2.0-restricted.7)

- Replaces separate-prefix `connection.rpc.handle` registration with the supported `connection.fetch.register` contribution at `/api/discord-remote-agents.manage`. The existing official `/api` carrier performs Host/Origin and browser-session admission before dispatch; the plugin adds no listener, cookie bridge, credentials or authentication exception. It does not replace the core interceptor or alter another service's injection.
- The Client still uses official Connection RPC, now with a namespaced endpoint and an outer success envelope carrying the strictly validated management reply. Management confirmation, revision checks, secret handling and unknown/no-replay behavior are unchanged. The exact route rejects mismatched methods, content types, malformed envelopes and bodies above 128 KiB without echoing inputs.
- A corrected isolated test using installed official Cordis/Connection, a provider without `webServer` injection and the actual plugin registered successfully and returned Host status with zero Native calls.
