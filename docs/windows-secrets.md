# Windows protected secrets — internal foundation and synthetic native verification

> **Historical foundation record.** Provider and threat-model details below remain applicable. Statements that management/GUI/receiver are entirely unwired describe the earlier foundation, not the approved [restricted profile](<limited-profile.md>). The current [Host](<../packages/discord-plugin/host-runtime.js>) uses this DPAPI provider with its own metadata settings/CAS and retirement queue; it does not claim the separate foundation SecretLifecycle journal as its active path. Independent owner/admin authorization remains unsupported. Current installation and local verification limits are in the [runbook](<restricted-installation.md>) and [verification record](<verification.md>).

## Delivered boundary

[Host-only provider](<../packages/discord-plugin/windows-secrets.js>) and [types](<../packages/discord-plugin/windows-secrets.d.ts>) add `WindowsSecretStore(root)` with `create(candidate)`, `read(ref)`, `retire(ref)`. The [fixed helper](<../packages/discord-plugin/windows-secrets.ps1>) calls .NET Framework `ProtectedData.Protect/Unprotect` with `DataProtectionScope.CurrentUser` and fixed domain entropy. Random 256-bit lowercase hex refs name only encrypted `.dpapi` blobs; no environment/DSH plaintext credentials/file fallback exists. There is no public RPC, owner grant, GUI wiring or receiver startup. Existing Host rejection and capability false declarations remain unchanged.

**Synthetic CurrentUser DPAPI and local SQLite fixtures passed under an accepted private workspace hierarchy; this is not complete PL-07/AC-25 or real-token deployment approval.** Unsafe TEMP fixtures still refuse. Real tokens require the intended deployment path, logging/threat-model review and formal owner/admin management boundary; no public secret operation is enabled.

## Storage / execution threat model

- Caller must choose a new plugin-specific root, never an existing credential file or arbitrary export destination. Local drive absolute path only; root drive, UNC, ADS, dot traversal, trailing dots/spaces, NUL and malformed refs are rejected. Existing root ACL is validated, not silently rewritten. Only missing root beneath an existing acceptable parent may be created; root is created using .NET's restrictive security descriptor, CurrentUser owner and only CurrentUser/SYSTEM FullControl. Blob names are server-generated and writes use CreateNew, no overwrite.
- Root/blob SID owner must equal current process user. Unexpected/deny ACEs on root/blob reject. Every existing ancestor rejects reparse points and untrusted DeleteChild/ChangePermissions/TakeOwnership grants; immediate parent also rejects untrusted Write/Delete. SYSTEM and built-in Administrators are trusted OS principals, not supported hostile attackers. Failures are whitelist-only constant codes: `PROTECTED_STORE_UNSAFE_PATH` (path/ACL/SID validation stage), `PROTECTED_LOGGING_POLICY`, `PROTECTED_API_UNAVAILABLE`, or `PROTECTED_STORE_FAILURE` (blob/protection operation), with no paths, raw exceptions, SID details, plaintext or ciphertext returned to logs.
- These checks are not kernel-handle-relative race-proof filesystem operations. Trusted same-user code or administrators can race paths/replace ACLs. A junction/symlink detected before operation fails closed; a sufficiently privileged concurrent attacker remains outside this threat model. Dedicated storage under a hierarchy without untrusted replacement rights is required. The provider is **not a sandbox**.
- DPAPI CurrentUser protects at-rest material from other unprivileged Windows users; **any code running as the same SID can decrypt it**, including a DSH shell/tool with that user's authority. This does not provide secrecy from arbitrary same-user agent code, malware, administrator/SYSTEM, memory inspection or browser/Host compromise. A separate OS user/broker or explicit product scope decision is necessary if that isolation is required. JS strings/base64 buffers cannot guarantee complete memory zeroization; the helper clears decrypted byte arrays but memory copies may remain.
- Fixed executable is `C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe`; installations with another Windows directory refuse rather than use PATH. The executable must be a regular nonsymlink file. Windows system binary and installed package JS are trusted; no Authenticode verifier or separate native broker is included.
- Helper source is SHA-256 pinned in the JS provider; the exact helper path is Git-pinned to LF in [attributes](<../.gitattributes>) so Windows fresh checkouts cannot silently change verified bytes. A non-native regression checks LF bytes against the provider's literal SHA-256 pin; verified bytes are encoded into `-EncodedCommand`, **not executed by a mutable helper path**, avoiding read/check/path-reopen TOCTOU for the script. Arguments contain only the fixed script, no candidate/ref/root. Candidate/ref/root are JSON over private stdin; decrypted result is private stdout to Host only. Environment is minimal fixed SystemRoot/WINDIR and contains no secrets. Stderr is discarded. Output bound 200,000 bytes; 15-second timeout kills only the owned helper and waits for close. No shell expansion or DSH process kill.
- PowerShell is a logging-sensitive carrier. Before reading stdin, helper checks HKLM/HKCU, 32/64 registry views for enabled Transcription, ModuleLogging and ScriptBlockLogging policy values; any enabled value or policy-read/API error refuses. `-NoProfile` avoids user profile startup transcription. This is not proof against arbitrary EDR, process instrumentation, local administrator tracing, or policies changed after check; those trusted-environment boundaries must be reviewed before real-secret use. Policy-enabled environments require another audited carrier (e.g. fixed compiled Windows helper), not disabling corporate logging. No such replacement/compiler dependency was installed here.

## Secret lifecycle / crash states

`SecretLifecycle(store, journal)` is an internal coordinator; `SecretJournal` is a product-owned durable CAS seam, **not an existing DSH API**. [SQLite journal](<../packages/discord-plugin/secret-journal.js>) adds `SQLiteSecretJournal.open(root)`, `load()`, guarded `compareAndSwap()`, `withExclusive()` and `close()`. It uses Node 22's built-in experimental SQLite, no added dependency. A dedicated private directory holds only two fixed databases and DELETE rollback journals. Windows applies the same restrictive SID/ACL/ancestor/logging gates as DPAPI before SQLite opens; existing directories/files are validated, never ACL-repaired. POSIX roots are owner-only with nonsymlink ancestry and no untrusted writable ancestor except root-owned sticky directories. SQLite stores reconstructed revision/ref/phase records only, discarding extra caller fields; no plaintext candidate or arbitrary metadata is persisted. These are Host-only APIs, never public RPC.

The state DB commits each CAS independently with `synchronous=FULL`. A separate guard DB holds `BEGIN IMMEDIATE` for the **entire** lifecycle operation including async verification and retirements. A competing coordinator/connection/process fails `SECRET_UPDATE_BUSY`; CAS alone is insufficient because recovery could otherwise delete a candidate being verified. There is no expiring lease or guessed dead PID takeover. Process termination releases SQLite's OS lock; committed pending state survives for explicit recovery. Closing an active journal is refused. A custom journal without `withExclusive` is rejected, not silently treated as safe. Dedicated local filesystems only; no network filesystem/adversarial same-SID/administrator or handle-relative race guarantee.

1. Require exact expected revision and no unresolved pending update. Serialize calls in one coordinator and require cross-owner durable journal CAS.
2. Store encrypted candidate with opaque ref. Journal pending `candidate` while retaining previous active ref.
3. Run a caller-supplied **read-only** verifier against Host-only read result. Verifier false/exception retires candidate, clears pending with CAS and preserves active ref. Raw verifier exceptions never escape.
4. CAS active ref to candidate, pending phase `switched`. Only then retire prior ref and CAS clear pending. Responses contain configured boolean/revision, never secret/ref/value.
5. Recover `candidate` by discarding unverified candidate (no automatic verifier/model replay), preserve old active ref. Recover `switched` by idempotent old retirement and journal completion. Invalid journal phase/reference relationships refuse before delete.

CAS/persistence/retirement failure leaves the corresponding pending state for explicit recovery; do not treat failure as success, do not start a receiver, do not retry model submission. Crash between blob create and journal prepare can leave an encrypted orphan; it is never auto-adopted. Failed CAS after verification leaves candidate pending. Every active/candidate/previous ref must be exactly 64 lowercase hex characters (type, length and case checked, no coercion/final newline); invalid relationships fail before any store deletion. Store-created refs must also be valid and distinct from the active ref.

`keep(expectedRevision)` is guarded read-only preservation. `delete(expectedRevision, true)` accepts no ref from a caller: it durably switches the active pointer to null with `deleting` pending containing only the journal-owned old ref, then retires that ref and clears pending. Literal confirmation, exact revision and no unresolved update are required. Recovery retries deleting retirement idempotently. This is an internal lifecycle contract, **not owner authorization or an exposed GUI management operation**, and it does not stop/cancel a receiver or DSH Run. Orphan GC, receiver generation lock/integration, key migration and backup policy remain pending. Blob deletion is not guaranteed secure erasure on SSD/backups; DPAPI key and encrypted backups have separate retention concerns.

## Separate admission-journal root

`prepareAdmissionJournalRoot(root)` adds a distinct Host-only helper operation for the [admission journal](<admission-journal-foundation.md>). It applies the same ACL/ancestor/logging gates but allows only `admission-(journal|guard).sqlite` and their DELETE rollback files. The existing `journal` operation still accepts only the secret-journal file set; the roots must remain separate. The admission module additionally rejects nonregular, symlink and multi-link files before SQLite opens, including on Windows. This does not change DPAPI behavior; the private-path evidence below is limited to fresh synthetic fixtures, not the intended deployment root. Updating the helper also updates its exact LF SHA pin.

## Separate text payload provider

[Protected text payloads](<protected-payloads-foundation.md>) use their own pinned helper and `payload-<64 lowercase hex>.dpapi` files with payload-specific CurrentUser DPAPI entropy. This is not an added token-helper operation: the token helper and its `450c940ede0ab72f136697644c951270a73c2a6f199c3ea69b34a08c0368c08d` LF pin remain unchanged. The payload provider rejects mixed roots, snapshots exact text/context before awaiting storage and verifies canonical encoding/digest/kind/context on Host-local reads. Opened-file Win32 identity checks reject observed hardlink/reparse/directory leaves; generic API/inspection/I/O failures are not unsafe-path fixture skips. It provides neither authorization, shared Native digest semantics, cleanup/retention, nor a same-SID/privileged-race sandbox. Final synthetic evidence and the separate payload-helper pin are recorded in [verification](<verification.md>).

## Durable journal verification limits

[Journal tests](<../test/plugin-secret-journal.test.ts>) exercise revision CAS, independent connection contention during verification, exact-ref rejection, scoped keep/confirmed delete, retirement failure recovery, no plaintext bytes, close/reopen, and child process exit **without closing the held guard** at candidate/switched/deleting boundaries. Durable cases run only when the fresh private fixture passes production path protection; refusal is reported as skipped/unverified, never native success. Tests never weaken ACL/logging gates or change existing ancestors. The default Windows TEMP hierarchy remains unsafe and those fixtures skip. Read-only ACL diagnostics found no corresponding dangerous grants on the workspace ancestry. During the Agent-budget increment, setting the test-only `DSH_DISCORD_TEST_PRIVATE_PARENT` to an existing safe workspace parent allowed three fresh fixtures through unchanged production gates: CurrentUser DPAPI dummy Unicode roundtrip/ciphertext-only/corruption/deletion, secret-journal reopen/connection contention/child-process exit and recovery, and admission-journal reopen/writer ownership/schema/byte-preservation cases. The separate Outbox increment also exercised its fourth fresh private fixture: sending-process exit to delivery_unknown, fence invalidation, retry time persistence, writer contention, schema/counter/state refusal and DB-byte preservation. The unified increment adds two more fixtures, covering actual product terminal transactions before/after COMMIT, rollback, cross-table pairing, duplicate counter identity, exact delivery state/version formulas, and replay with a recreated random protected-ref preserving the original snapshot/ref. No existing ACL was changed; fresh fixture directories were removed. This is local fixture evidence, not power-loss durability, hostile same-SID isolation, live Host integration or acceptance of an arbitrary deployment root. Missing/unusable configured parents can fail fixture setup; there is no automatic fallback.

## Owner authorization design (not implemented)

Existing DSH Connection Cookie and single operator Peer are not owner/admin proof. No payload userId or GUI session can grant a management capability. Existing foundation dispatch continues always rejecting without authority.

Historical Phase 2 sketch (not the adopted current bootstrap; see the [upstream owner/admin contract](<p0-management-authorization.md>)): explicit Windows local interactive approval in the intended CurrentUser session, verifying actual SID and Host instance nonce through a trusted local surface. Bind a short-lived, single-purpose unpredictable capability to Host generation, exact same-origin authenticated Connection peer and operation scope. Require independent CSRF nonce plus Origin/Host admission; no URL/localStorage persistence; expire within a few minutes, revoke on logout/disable/restart/owner change. Issuance requires real trusted interaction—not a boolean supplied by Client. Audit only constant outcomes. Cross-SID sessions, replay, capability theft, shared browser session and relay must have negative tests. No local owner prompt/UI was launched, no authority module grants access and no management endpoint is published in this phase.

Future GUI contract: send transient candidate exactly once under verified management authority; clear password field immediately after send/unmount; receive only sanitized revision/configured/status, never `read()` output. Blank means keep, deletion requires explicit confirmation. Read-only Bot identity verification must not register slash commands/start receiver/submit a model prompt. Protected-store readiness and authenticated owner readiness are separate gates.

## Experiments / verification

[Tests](<../test/plugin-secrets.test.ts>) cover lifecycle ordering, failed verifier, revision mismatch, pending candidate/switch recovery, busy rejection, journal-error sanitization, invalid journal protection, invalid refs/paths and a native dummy-only attempt. Each native attempt generates a new UTF-8 Japanese/emoji/random dummy, uses only a fresh temporary directory, and verifies the resolved absolute cleanup target before deleting it. No real Discord/DSH token or existing credentials/config/store is read; the dedicated test-only environment variable selects a fixture parent, not a credential.

Initial `npm test`: 49 pass / 1 fail. Native create refused `PROTECTED_STORE_FAILURE`; inspecting only TEMP ACL metadata showed additional CodexSandboxUsers/SID Modify/FullControl entries inherited by fixtures. Attempt to provision only the fresh fixture ACL failed with sanitized constructor/identity-mapping error (`NATIVE_FIXTURE_UNAVAILABLE_RULE`); existing TEMP ACL was never changed. Fixed rule construction to explicit SecurityIdentifier and strengthened ancestor DeleteChild checks instead of weakening guards. Because hostile rights on the ancestor remain, removed fixture-ACL alteration: a private leaf cannot fix an unsafe ancestor. Native test now asserts refusal emits constant error/no files and marks roundtrip explicitly **skipped/unverified** if the fixture is refused. This is not a mocked DPAPI success.
